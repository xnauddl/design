## 불합격 1 — Space between 간격 (가드)

현상
- 주 축 정렬이 Space between(`primaryAxisAlignItems = 'SPACE_BETWEEN'`)인 오토레이아웃은 피그마가 `itemSpacing`을 쓰지 않는다(간격 자동).
- 그런데 `src/lib/extract.ts` `collectSpacing`이 그 값을 그대로 뽑아 쓰레기 Global 토큰이 생겼다: `spacing/33` · `spacing/51` · `spacing/109` · `spacing/198` · `spacing/257`.
- `src/lib/bind.ts`가 `itemSpacing`에 변수를 붙이자 피그마가 정렬을 왼쪽(MIN)으로 바꿔 카드 간격이 40 → 33으로 바뀌었다. §2.11 "레이어 값을 바꾸지 않는다" 위반.

수정 스펙
1. `collectSpacing`: `primaryAxisAlignItems === 'SPACE_BETWEEN'`이면 `itemSpacing`을 건너뛴다(padding은 그대로). wrap 레이아웃은 `counterAxisAlignContent === 'SPACE_BETWEEN'`이면 `counterAxisSpacing`을 건너뛴다.
2. `bind.ts`: 같은 조건에서 두 필드를 건너뛰고 사유 `space-between`을 남긴다. i18n `reason.space-between` = "사이 간격 자동"(연결 화면 건너뜀 칩 문구 길이에 맞춤. 검수자 제안 "사이 간격 자동(Space between)이라 gap을 연결하지 않음"을 줄임).
3. 테스트: Space between 프레임 1개 → gap 토큰 없음, 연결 뒤 `primaryAxisAlignItems` 그대로, 사유 기록.

## 불합격 3 — 컴포넌트 인스턴스가 페이지 맨 위로 (출시 블로커)

현상(레이어 › 컴포넌트: 후보 스캔 → 등록)
- 구조가 `FRAME > GROUP > VECTOR×2~3`인 아이콘 6개(tabler:world, tdesign:location, solar:calendar-broken×3, tabler:pig-money)가 실패.
- 인스턴스 13개(ItemIcon 7 · HeaderIcon 2 · ArticleIcon 4)가 원래 자리 대신 **Page 1 맨 위 (0,0)** 에 생겼다.
- 원본 벡터는 사라졌다(VECTOR 19 → 6, GROUP 6 → 0).
- `FRAME > VECTOR` 직속 아이콘(octicon:people-16, ant-design:safety)은 제자리에서 잘 바뀌었다.
- 화면에 "인스턴스 배치 실패" 오류가 보였다.

검수자 추정(미확인): 원본 벡터를 먼저 지움 → 자식 0개가 된 GROUP을 피그마가 자동 삭제 → 부모가 없어 `insertChild` 실패 → 페이지 맨 위로 대체. `src/lib/similarApply.ts`의 "원래 index에 insertChild"가 이 경우를 못 다룸.

원인 확인(코드, 2026-11-04)
- 실패한 곳은 `similarApply.ts`([묶기])가 아니라 **[등록]** 경로 `src/code.ts` `REGISTER_COMPONENTS`다. "인스턴스 배치 실패" 문구는 그 안의 `restore`에만 있다.
- 벡터 아이콘은 리네임이 `icon` 역할을 단 **말단(VECTOR)** 이라 등록 후보가 된다(FRAME/GROUP은 고신뢰 구조만 후보). 그래서 그룹 안 벡터 2~3개가 각각 멤버다.
- 순서: `captureOrigin`이 부모(=GROUP)와 index를 적어 둠 → `figma.createComponentFromNode(벡터)` → 세트 결합(`combineAsVariants`) · Components 페이지로 이동(`placeOnPage`) · 속성 접힘의 비마스터 `remove()`로 벡터가 그룹 밖으로 나감 → 한 그룹의 벡터가 모두 같은 등록 그룹이면 그룹의 자식이 0이 되어 피그마가 GROUP을 지움 → `restore`의 `o.parent.insertChild`가 던짐 → `catch`가 "인스턴스 배치 실패"만 남김.
- 인스턴스는 `createInstance()`가 처음 놓은 **현재 페이지 맨 위 (0,0)** 에 그대로 남는다(대체 코드가 따로 있는 게 아니라, 옮기지 못한 인스턴스를 치우지 않았다). `o.parent`가 없을 때(`skipped++; continue`)도 같다.
- 직속 `FRAME > VECTOR`가 멀쩡했던 이유: 빈 FRAME은 피그마가 지우지 않는다.
- 검수자 추정의 "원본 먼저 지움 → 빈 GROUP 자동 삭제 → insertChild 실패"는 맞다. 다만 파일은 `similarApply.ts`가 아니라 `code.ts`이고, [등록]에서 원본은 지워지는 게 아니라 **컴포넌트가 되어 Components 페이지로 옮겨진다**.
- `similarApply.ts`([묶기])는 이미 "넣고 나서 지우기" 순서였지만, 부모가 없으면 인스턴스가 페이지 맨 위에 남고(`if (parent)` 밖), 넣기가 던지면 `catch`가 인스턴스를 치우지 않는 같은 종류의 구멍이 있다 — 함께 고친다.

수정 스펙(검수자) → 명세 §4.7 "인스턴스 자리"
1. 인스턴스를 먼저 같은 부모 같은 index에 넣고 x/y(와 제약)를 복사한 뒤 원본을 지운다.
2. 부모가 GROUP이면 `absoluteTransform` 기준으로 위치를 보정한다(그룹 자식 좌표).
3. 페이지 맨 위로 대체하지 않는다. 넣기 실패 시 원본을 지키고, 결과에 `placeFailed` 수와 이름을 넣어 UI 결과 줄(i18n)에 보인다.
4. 테스트: `frame > group > vector` → 인스턴스가 같은 프레임/그룹의 같은 위치, 페이지 맨 위 자식 수 그대로, 노드 수 그대로. `FRAME > VECTOR`도 그대로 동작.

[등록]에서 "원본을 지키기"는 그대로는 안 된다(원본 노드 자체가 컴포넌트가 된다). 그래서 명세는 원본을 바꾸기 전에 그룹 안에 빈 표지를 넣어 그룹을 지키고, 그래도 실패하면 인스턴스를 지우고 이름을 알리는 것으로 정했다(§4.7 5번).

다시 실행했을 때 기대값: Page 1 맨 위에는 프레임만, 아이콘 위치는 원본과 같음, 노드 수 256.
